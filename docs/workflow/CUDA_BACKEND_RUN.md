## 1. Purpose
A 4-layer agentic delegation pipeline (USER → Hand → Orchestrator → Lead → Native sub-agents) that drives any declared end-state to completion using vee as the single source of truth, with **100% traceability** via per-agent sessions and PostToolUse tool-call capture.

## 2. Layer boundaries

```
  USER
    │
    ▼
  HAND ────────────── owns END STATE. Seeds goal + status + missions. ONE vee agent spawn.
    │ vee agent spawn + session handoff
    ▼
  ORCHESTRATOR ────── owns CURRENT STATE. CAN vee agent spawn AND Task().
    │ vee agent spawn + session handoff
    ▼
  LEAD(s) ─────────── owns a SCOPED SLICE. CANNOT vee agent spawn. CANNOT write code.
    │ Task(subagent_type=…) — captured by PostToolUse hook
    ▼
  NATIVE SUB-AGENTS ── Write code, run tests, record learnings, close missions.
                       Tool calls captured by parent pane's PostToolUse hook,
                       tagged with lead's session id.
```

## 3. Permission matrix

| Layer           | vee agent spawn  | Task() | Writes code |
|-----------------|------------------|--------|-------------|
| Hand            | 1× (Orchestrator)| no     | no          |
| Orchestrator    | yes              | yes    | no          |
| Lead            | NO               | yes    | no          |
| Native sub-agent| no               | no     | YES         |

## 4. Status vocabulary

| Signal | Meaning                               | Check                                              |
|--------|---------------------------------------|----------------------------------------------------|
| Green  | Goal achieved                         | latest status decision has `State: ACHIEVED`       |
| Amber  | Mission in_progress                   | `vee mission list --status in_progress` non-empty  |
| Red    | Mission ready (actionable, unclaimed) | appears in `vee mission ready`                     |
| Gray   | Mission open but dep-blocked          | in `list --status open`, not in `ready`            |

## 7. Traceability guarantees (v2)

### 7.1 Per-agent sessions (Level 1)

Every agent (Hand, Orchestrator, Lead) opens its own vee session as its first action (Step 0 in every charter):

```bash
<ROLE>_SESSION=$(vee session open \
    --role <role> --task $GOAL_TAG \
    --parent $PARENT_SESSION \
    --capture=native --capture-pane $TMUX_PANE \
    --json | jq -r '.data.session_id')
```

Every subsequent vee command passes `--session "$<ROLE>_SESSION"` so all records carry authorship.

### 7.2 Session tree

```
supervisor (root, role=hand-supervisor)
  └─ hand                 (role=hand,         parent=supervisor)
       └─ orchestrator    (role=orchestrator, parent=hand)
            ├─ scout-lead-1 (role=lead, parent=orchestrator)
            ├─ scout-lead-2 (role=lead, parent=orchestrator)
            └─ exec-lead-N  (role=lead, parent=orchestrator)
```

Each parent/child pair is linked explicitly via `vee session handoff --session $PARENT --to <child-pane-name> --scope "<reason>"`.

### 7.3 Pane capture (Level 2)

`vee session open --capture=native --capture-pane $TMUX_PANE` spawns a detached capture worker that streams the pane's stdout/stderr into vee under the session. Set once at session-open; no second command needed.

### 7.4 Tool-call capture (Level 3)

`.claude/hooks/posttooluse-vee-log.sh` runs after EVERY Claude Code tool call (Bash, Read, Edit, Write, Task, …) and writes a canonical vee record:

- Tagged: `tool-call`, `trace`, `pane-<id>`
- Session: resolved from `.vee/pane-sessions/<pane-id>` marker written by the agent's Step 0
- Body: `tool=<name> pane=<id> status=<ok|fail> args_sha=<8> result_bytes=<N>`
- Fire-and-forget (never blocks the pane; `set +e`)

Sub-agents (`Task()` children) run INSIDE their parent pane's Claude context — their tool calls are captured by the SAME hook and get the SAME session id as their parent lead. That's by design: sub-agents are logically part of their lead's work.

### 7.5 Pane-session marker protocol

Each pane's Step 0 writes its session id to `.vee/pane-sessions/<TMUX_PANE-stripped-of-percent>` so the PostToolUse hook can resolve which session owns which pane. `%` stripped for filename safety.

## 8. Event flow for the CUDA run

1. USER → HAND: provides GOAL_TAG, GOAL_TITLE, GOAL_BODY.
2. HAND Start Sequence: session.open → existing-goal probe → seed end-state + status (Baseline=UNKNOWN) → seed missions.
3. HAND Mission In Flight: token-count payload → spawn ORCHESTRATOR → onboard → session.handoff → start.
4. ORCHESTRATOR Start Sequence: session.open → query end-state → prime → read status → routes on Baseline.
5. Discovery D1–D8: decompose → lead count → record discovery-plan → spawn scouts (each opens its own session) → monitor → fact-check → supersede status Baseline=KNOWN → kill scouts.
6. Execution E1–E5 loop: read state → classify → delegate (Task or Lead) → verify closure → continue.
7. Execution E6: spawn validator → PASS → supersede status ACHIEVED + VERIFIED → message HAND.
8. HAND → USER: reports Green.

   ```
   jq -r 'select(.event_type=="session.open") | "\(.entity_id) role=\(.payload.role) parent=\(.payload.parent_session_id)"' .vee/records/events/0001.log
   ```

   ```
   jq -r 'select(.event_type=="record.upsert") | .actor.agent_id' .vee/records/events/0001.log | sort | uniq -c
   ```

3. Tool-call records per session:
   ```
   vee query "tool-call" --mode lexical --limit 100 --json
   ```

4. Pane-session marker snapshot:
   ```
   ls .vee/pane-sessions/
   ```
